# Системный дизайн обмена валют внутри кошелька

## 1. Назначение

Решение позволяет авторизованному пользователю обменивать средства между валютными счетами собственного внутреннего кошелька. Пользователь выбирает направление обмена, вводит сумму списания, получает ограниченную по времени котировку, подтверждает условия и получает однозначный результат операции.

`index.html` и `test6 - CODEX.html` — интерактивный интерфейс. При запуске через `server.py` он загружает балансы и выполняет обмен через локальный API, сохраняющий результат в SQLite. Самостоятельно открытый HTML остаётся mock-прототипом. Реальные финансовые операции не выполняются.

## 2. Границы решения

В рамках решения:

- получение балансов и доступных валютных пар;
- создание котировки с ограниченным сроком действия;
- расчёт суммы получения и комиссии;
- проверка суммы, лимитов и доступного баланса;
- создание и выполнение заявки на обмен;
- обработка изменения и истечения курса;
- идемпотентная отправка заявки;
- атомарное списание и зачисление;
- получение статуса и результата заявки;
- аудит ключевых событий.

Вне рамок: регистрация, KYC/AML, пополнение и вывод, покупка с карты, управление курсами, полная история кошелька и отмена уже исполненного обмена.

## 3. Основные компоненты

| Компонент | Ответственность |
| --- | --- |
| Web UI | Ввод данных, отображение балансов, котировки, ошибок и результата |
| API Gateway | Авторизация, маршрутизация, корреляция запросов и ограничения частоты |
| Wallet Service | Балансы, резервирование, списание и зачисление средств |
| Rate Service | Актуальные курсы и доступность валютных пар |
| Exchange Service | Котировки, проверки, заявки, идемпотентность и оркестрация обмена |
| Order Repository | Заявки, статусы, зафиксированные условия и даты |
| Audit Log | Неизменяемый журнал бизнес-событий и результатов |

Текущий backend использует фиксированный демонстрационный курс, один кошелёк и не имеет авторизации, внешнего Rate Service или Audit Log. Следующие разделы описывают целевой дизайн, если это явно не указано иначе.

## 4. Бизнес-правила

1. Валюты списания и получения различаются и образуют поддерживаемую активную пару.
2. Сумма списания положительна, соответствует точности исходной валюты и лимитам пары.
3. Сумма списания, включая комиссию по выбранной модели, не превышает доступный баланс.
4. Комиссия включена в введённую сумму и удерживается в исходной валюте.
5. Для подтверждения используется только активная котировка, связанная с суммой и направлением обмена.
6. Котировка действует 30 секунд. Истёкшая котировка не продлевается и не используется автоматически.
7. Изменение курса требует новой котировки и явного повторного подтверждения.
8. Один ключ идемпотентности соответствует одной логической попытке создания заявки.
9. Списание и зачисление выполняются атомарно.
10. Денежные расчёты выполняются в целых minor units либо decimal-типом без двоичной плавающей точки.

## 5. Расчёт суммы

Курс задаётся в направлении `1 USDT = rate RUB`.

Для RUB → USDT:

`targetAmount = round((sourceAmount - commissionRUB) / rate, 2)`

Пример: `(10 000,00 - 50,00) / 92,40 = 107,68 USDT`.

Для USDT → RUB:

`targetAmount = round((sourceAmount - commissionUSDT) × rate, 2)`

В mock-прототипе базовая комиссия 50 RUB переводится в исходную валюту по курсу котировки. При курсе 92,40 она составляет 0,54 USDT. Пример: `(100,00 - 0,54) × 92,40 = 9 190,10 RUB`.

Округление выполняется один раз для итоговой суммы по математическому правилу до двух знаков. В production точность должна определяться справочником валют.

## 6. Котировка

Котировка содержит `quoteId`, валютную пару, сумму списания, комиссию, курс, сумму получения, время создания и `expiresAt`. Она имеет состояние `ACTIVE` или `EXPIRED`.

При изменении суммы или пары клиент запрашивает новую котировку. После истечения UI блокирует подтверждение и предлагает получить новую. Сервер повторно проверяет срок действия при создании заявки, поэтому время клиента не является источником истины.

В HTML-прототипе идентификатор и таймер котировки создаются локально. SQLite-режим фиксирует условия обмена при выполнении и сохраняет уникальный идентификатор заявки. Полноценная серверная котировка с TTL пока не реализована.

## 7. Жизненный цикл заявки

| Статус | Значение |
| --- | --- |
| `CREATED` | Заявка зарегистрирована, условия зафиксированы |
| `PROCESSING` | Выполняется атомарное изменение балансов |
| `COMPLETED` | Списание и зачисление завершены |
| `REJECTED` | Нарушено бизнес-правило |
| `FAILED` | Возникла техническая ошибка, частичных изменений нет |

Переходы: `CREATED → PROCESSING → COMPLETED`; альтернативно `CREATED → REJECTED` или `PROCESSING → FAILED`. Терминальные статусы не изменяются повторной отправкой того же идемпотентного запроса.

## 8. Сценарии

Основной сценарий: UI получает балансы, создаёт котировку, пользователь проверяет условия и подтверждает обмен. Exchange Service повторно проверяет котировку и баланс, создаёт заявку, атомарно изменяет оба баланса и возвращает `COMPLETED`.

Негативные сценарии включают недостаточный баланс, некорректную сумму, истёкшую котировку, изменение курса, повторную отправку и техническую ошибку. Детальные критерии приведены в `scenarios.feature`.

## 9. Повторная проверка баланса

Баланс проверяется при создании котировки для ранней обратной связи и повторно внутри операции создания заявки. Вторая проверка обязательна, поскольку между расчётом и подтверждением баланс мог измениться. При недостатке средств заявка отклоняется без списания.

## 10. Изменение курса

Если сервер не может принять исходную котировку, он возвращает конфликт с причиной `QUOTE_CHANGED` и, при возможности, новую котировку. UI показывает старые и новые условия. Новая заявка создаётся только после отдельного действия «Подтвердить новый курс».

## 11. Идемпотентность

Клиент передаёт `Idempotency-Key` при `POST /api/v1/exchange-orders`. Сервер сохраняет соответствие ключа, пользователя, нормализованного тела запроса и результата.

- повтор с тем же ключом и тем же телом возвращает ранее созданную заявку;
- повтор с тем же ключом и другим телом возвращает `409 IDEMPOTENCY_CONFLICT`;
- блокировка кнопки в UI снижает риск повторного клика, но не заменяет серверную идемпотентность.

## 12. Атомарность и согласованность

Списание исходной валюты, зачисление целевой валюты и фиксация результата заявки выполняются в одной транзакционной границе либо через эквивалентный механизм гарантированной оркестрации. При ошибке обе денежные проводки откатываются. Аудит не должен ошибочно фиксировать успешный обмен до подтверждения транзакции.

## 13. Ошибки

| Категория | Примеры | Поведение |
| --- | --- | --- |
| Формат запроса | отсутствует поле, неизвестная валюта | `400` |
| Конфликт | истёкшая/изменившаяся котировка, конфликт ключа | `409` |
| Бизнес-валидация | недостаточно средств, нарушен лимит | `422` |
| Техническая ошибка | недоступен Rate или Wallet Service | `503` |

Ответ содержит стабильный код и понятное сообщение без внутренних деталей. Технические сведения связываются через `traceId` и журналируются на сервере.

## 14. Нефункциональные требования

- финансовые значения не используют binary floating point;
- операции изменения баланса атомарны и идемпотентны;
- пользователь определяется из контекста авторизации;
- все запросы выполняются по TLS, чувствительные данные не журналируются;
- ключевые действия имеют корреляционный идентификатор и аудит;
- UI поддерживает клавиатуру, достаточный контраст и текстовые обозначения состояний;
- основной desktop-сценарий не имеет горизонтальной или вертикальной прокрутки;
- целевые показатели доступности и времени ответа должны быть согласованы отдельно.

## 15. Допущения и открытые решения

- пользователь авторизован и имеет активный кошелёк;
- в первой версии поддерживается RUB/USDT в обоих направлениях;
- TTL котировки равен 30 секундам;
- комиссия включается в сумму списания;
- прототип использует два знака после запятой для обеих валют;
- production-источник курса, лимиты, правила комиссии и срок хранения идемпотентности требуют согласования;
- синхронное выполнение показано в UI, но API допускает получение промежуточных статусов через `GET`.
